## Decisions

- `clarc` is a new Rust binary crate `packages/clarc` in the cargo workspace. Depends on `c43-layout` (engine) and on the `c43` library for the shared drawio exporter (text measuring, header band, frame, edges), which gains a drawing-strategy parameter (functions for drawing a node, a group and an edge) instead of being copied. c43's own output stays byte-identical.
- CLI: `clarc [--aws|--azure] [--file <path>]`; stdin when no `--file`; drawio XML on stdout; warnings (dropped things, unsatisfied hints, layout rule violations) on stderr; exit 0 with warnings, non-zero on bad input. `--aws` is the default.
- Input is JSON, the engine's compound graph extended with a cloud `service`, and a separate `hints` section keyed by node id:
  - `title`, `description`, `groups[{id,label,service?,group?}]`, `nodes[{id,label,service?,group?}]`, `edges[{from,to,label?,kind?,style?}]`, `hints{<id>:{start?,leftOf?,rightOf?,above?,below?,sameRow?,sameCol?}}`. Unknown fields are rejected.
  - `service` keys are provider-neutral (`client server cdn dns object-storage vm function container-service container-registry api-gateway role parameter-store ops-console monitoring topic email query private-endpoint static-ip note`; group frames `network region cloud group`) with provider-native aliases (`cloudfront`, `s3`, `ssm-parameter-store`, `front-door`, …). One input therefore renders under `--aws` and under `--azure`; each theme maps a key to its own icon, colour and frame. A node without service, or with an unknown one (warning), is a bordered note.
  - A service is either data or nf (non-functional: DNS, registry, role, parameter store, monitoring, topic, ops console). An edge is nf if an end is nf, else data; an explicit `kind` wins. nf edges are dashed unless `style` says otherwise. Engine consequence: data flows left→right, nf up→down, nodes with only nf edges go to the bottom band unless hinted.
  - `hints`: `start:true` = the left-most node, carried as the engine's single priority hint; the others are plain suggestions (`a <rel> b` with `a` the keyed node). More than one `start` or an unknown id → error.
- Placement hints (moth m1ei4) are implemented in this task inside `c43-layout`: relations `left-of right-of above below same-row same-col`, unary `leftmost`, one `priority` flag (priority wins; more than one → error; unknown id or malformed → error). Suggestions only: a hint that the final layout does not satisfy is listed in `metrics.ignored_hints` (omitted when empty, so hint-free output is unchanged). Hints may cross group boundaries: at each group level an end is lifted to the child that holds it; hints inside a single child belong to that child's level. A group-level hint holds for the group block, not for each member (e.g. same-row with a group does not align a member).
  - Mechanism: leftmost = no incoming layering edge; left/right = extra layering edge unless it would close a cycle (real edges take precedence); same-col = pull into the other's layer when its edges allow; above/below/same-row = row adjustments after the column order is known (also for nf nodes); the node-move repair never makes a hint worse. Implemented hints stay out of the way of hint-free layouts (byte-identical goldens).
  - Row hints are applied in a fixed order: same-row first (they define the rows; hints already linked by same-row move together, so Viewer ↔ CloudFront ↔ VPC chains hold), then above/below, then the priority hint. Same-row moves the keyed node (`a`) onto the other node's row; for above/below the subject (`a`) likewise moves, into the nearest free row slot beyond the other node. The other node stays put, and whatever is already lined up with the moving node by same-row hints moves with it, so a later above/below never leaves a row-mate behind. Rejected: swapping rows in a shared column (it dragged linked nodes off their row); applying hints in input order (a later same-row undid an earlier below).
  - Across a group boundary a plain node with a same-row hint to a member of a sibling group block lines up with that member (within its row span), and plain nodes linked to it by same-row follow. Rejected: lifting the hint to the block only (the node was then centred on the block and never level with the member).
- Layout rules added for the cloud look (engine, apply to every graph):
  - A source is a node with no incoming edge of either kind. A data node without data predecessors but with an incoming nf edge is no source: it joins its nf predecessor's column (below it, since nf runs downward) and whatever it feeds moves one column right so data edges keep pointing right; the node-move repair keeps only true sources from being pushed right. Rejected: letting `same-col` pull a source into another node's column (it fixed one pair, but pushed that node's successors into a messy right side; the nf rule is general).
  - Story reading left to right: when a `leftmost` (start) node has exactly one outgoing data edge, it ends up on that target's row. Done after the repair as a final step (flat layouts swap the two nodes' rows, grouped layouts only move into a free cell), not as an implicit hint. Rejected: an implicit same-row hint (it stops the repair from moving either node, which left phase 2 stuck in a worse layout with a long loop edge) and moving linked row-mates together inside the repair (no gain). Without a start hint nothing changes.
  - Edge ends are attached to the icon, not to the node square that also holds the label: left and right ports are spread over the icon's height; a single port facing a busier port on the same row (one output into a many-port input, or many outputs into one input) takes the busier port's height so the edge is a straight line; the waypoints of the horizontal run leaving a moved end move with it (a path that is one run is split between its two ends), so no edge is skewed.
  - Gravity: connected nodes gravitate and connections want to be short. A layout preference (`gravity`, off in c43 so its hint-free goldens stay, on in clarc): after the grouped grid is built, a top-level node with only nf edges that is pointed at by a member of a group moves to the nearest free cell outside every group frame, at or right of and at or below that member (right first on a tie), and empty rows and columns are dropped. Without it such nodes sit in the bottom band, under the whole group block, however far from the member. Explicit placement hints on the node win over gravity. Rejected: gravity in the flat placement (the repair already pulls such nodes in) and a repair guard (not needed); an ssm "above ec2" fixture hint (it only mimicked the reference diagram and held the node away from its source).
  - A level pair (single port facing a busier one, same row, nothing on that row between the two nodes) is drawn as one straight line without the engine's waypoints, since the engine routed it through a lane because its own ports were at different heights. With a node in between the engine's route stays.
- Look of a node: invisible square (the engine's node) holding a fixed-size icon at the top and the label below it; edges attach to the icon side (the end is pulled in from the square's border; the engine's end point stays as a waypoint so lines remain orthogonal). Notes are the square itself with the label inside (side capped so that one long note does not enlarge every node). Label wrapping decides the node side (min 5 units of 20 px). Group frames: aws group shape with the group icon (VPC purple) and a coloured bold title, azure dashed blue frame, generic grey. Edge labels have a white background.
- Icons: aws4 resource icons/shapes and the `img/lib/azure2/` images built into drawio; names verified against drawio's own stencil/image sources (some natural-looking names do not exist, e.g. `elastic_ip_addresses`; the correct `elastic_ip_address`, `parameter_store`, `cloudwatch` are used). Nothing embedded.
- Scope of the first deliverable: AWS for the two reference architectures (ghosted phase1 "Ghost on a VM", phase2 "managed, containerized, stateless") plus an Azure replica of phase2 (neutral service keys, Azure labels). Not 1:1 with the references: Viewer left-most, icons with labels, VPC frame, dashed nf/control links, labelled edges, notes; no hand-placed coordinates.
- Fixture hints used as the model of how a user or agent drives the tool: phase1 — Viewer start, site above cf, r53 below cf, VPC origin right of and on the same row as cf, ec2 right of origin; phase2 — Viewer start, site above cf, ecr above ls, r53 below cf, data right of site and on its row, role below ls, cw below role. No warnings expected on any fixture except the known limits below.
- Acceptance: fixtures `input.json` + golden `expected.drawio` for `phase1`, `phase2`, `azure-phase2` under `packages/clarc/tests/cases`; tests assert golden equality (`UPDATE_GOLDEN=1` rewrites), that the start node is left-most and no hint is ignored, theme icon sets, service aliasing, kind derivation, input errors, that edge ends lie on the icon and straight edges stay straight, and that a single port facing a busy one on the same row is level with it (both directions). Engine tests cover: nf-fed node follows its predecessor while a node without any incoming edge stays a source; same-row with a group member; same-row winning over an earlier below; the start node level with its single target (flat and through a group) and no such rule with two targets. Renders for eyeballing via `scripts/render.sh`. e2e (local-docker) pipes an input through `clarc --azure`.
- Process rule adopted in this task: a detected bug always gets a regression test that fails before the fix and passes after (recorded in CLAUDE.md).
- Known limits, accepted: the engine can still report `crossing`/`through-title` violations on other inputs (warnings only); edge labels can sit over a neighbouring icon label; hints on a nf node only influence rows, not columns; a single port is levelled (and drawn straight) only for a facing right→left pair on the same row (not top/bottom pairs in a column); a hint that fights another stays a reported suggestion; the node-move repair is a hill climb over single steps (one cell, or a swap with the occupant), so a better layout that needs a long jump or a swap of two distant nodes (e.g. phase 2: the IAM role and the SMTP server, which would shorten the role → data-bucket edge) is not found; pairwise swaps (opt-in, behind `gravity` to keep c43's goldens) or a hint are the way out.

## Implementation (abstract)

- Parse input → map each service to (icon, colour, nf) per theme → build engine graph + hints (edge kinds from services/explicit, node sizes from label wrapping, group title widths including the group icon, placement from node hints) → engine layout → render through the shared drawio exporter with the cloud drawing strategy → stdout; violations and unsatisfied hints → stderr.
- Layout rules: gravity is a final step on the grouped grid; the layering step treats nf-fed data nodes as followers of their nf predecessor; a final step after repair levels the start node with its single target; the exporter shifts waypoints with moved ends; clarc maps a port's slot to a position on the icon and, for a level pair, reuses the busier end's slot for the single end.
- Placement hints: the model carries a list of relative hints into the normalized graph; skeleton (layering), placement (rows), repair (move guard), hierarchy (lifting to group levels) and the engine's final check (ignored list) consult it only when it is non-empty.
